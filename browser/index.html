Give your agents a browser.

Some work has no API. Dashboards, logged-in tools, forms, the whole human web. This skill gives an agent a real, headed Chromium (or Chrome) it can drive with nothing but the DevTools Protocol: read, click, type, verify. No Playwright, no Puppeteer.

The method

Eight moves, each learned in production. The theme of all of them: never assume, always verify with a read.

01Launch

Chromium-first, cross-platform (macOS and Linux first-class; Windows not supported). Resolve the binary, never hardcode one:

resolve_browser() {
  [ -n "$CDP_BROWSER" ] && { echo "$CDP_BROWSER"; return; }
  for c in \
    "/Applications/Chromium.app/Contents/MacOS/Chromium" \
    "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"; do
    [ -x "$c" ] && { echo "$c"; return; }
  done
  for c in chromium chromium-browser google-chrome-stable google-chrome; do
    command -v "$c" >/dev/null && { echo "$c"; return; }
  done
  return 1
}

"$(resolve_browser)" \
  --remote-debugging-port=9222 \
  --user-data-dir=$HOME/.cache/cdp-profile-example \
  --no-first-run --no-default-browser-check \
  "https://example.com" &
  • Why this order: an explicit CDP_BROWSER override wins; then Chromium (package-manager installable, no auto-updater, open source); then Chrome, because most desktops already have it, it ships the proprietary codecs (H.264/Widevine) some sites need, and Google sign-in is friendlier to branded Chrome. Vanilla Chromium can hit "this browser may not be secure" on Google logins, which matters for a skill whose whole point is logged-in sessions.
  • Always a dedicated --user-data-dir, never the user's main profile. It persists logins across relaunches.
  • Headed, so a human can watch and solve a login or 2FA once.
  • Capture the PID; stop it by exact PID only, never by name. The authoritative liveness check is lsof -ti :<port>.

02Connect & discover

GET /json on the debug port lists targets; pick type === "page" and the URL you want, then attach with chrome-remote-interface and enable Runtime + Page.

03Read the page

One IIFE returning a single JSON.stringify'd payload. Always sweep for warnings: [role=alert], aria-invalid, text near "error" and "failed". Red text is critical information: surface it, never skip it. An empty table is not proof of absence: check the active filters first.

04Wait correctly

document.readyState === "complete" does NOT mean a SPA has rendered. Poll your own condition (selector present, rows > 0) every 1.5–2.5s up to a budget, from inside one process. Never sleep blindly when a poll can decide.

05Click safely

  1. Find the element by accessible text or role, scroll it to center.
  2. Probe before clicking: elementFromPoint(x,y) must carry the EXACT expected text; mismatch means abort and re-locate.
  3. Dispatch the click, then verify the effect with a read.

Never act on a table row by index: virtualization re-maps rows. Verify the row's entity name in-DOM first.

06Type into modern apps

Plain el.value = "x" does not register in React or Vue. Use the native value setter + input/change events; for contenteditable, send real keystrokes. Editors lie: after any important entry, save, reopen, and verify it persisted.

07Screenshot

Page.captureScreenshot, then actually LOOK at it. Layout, red banners, and truncation are invisible in innerText. On HiDPI screens, scale coordinates by the pixel ratio before mapping a screenshot position to a click.

08Discipline

  • Separate reads from mutations; disclose even view-only changes when the task says "don't change anything".
  • Restricted to specific domains means navigate ONLY those.
  • After any UI mutation, verify through an independent channel (API/CLI) when one exists. The UI's own confirmation is not proof.

The session law

The capability is the easy half. What separates this from naive browser automation is the discipline: this law exists because of a real incident, where an agent used a browser session belonging to another agent and posted from the wrong account. It was caught minutes before real damage. In a multi-agent fleet, this is the failure mode that turns automation into liability.

⚠ Sessions are personal

  1. One agent = one browser session = one profile = one port. A profile dir and debug port belong to one agent for the lifetime of its role. Profiles are persistent: platform logins live in them and survive relaunches. Treat another agent's session like another person's logged-in phone: never touch it.
  2. Never reuse or attach to another agent's session: not its port, not its profile dir, not its running Chrome, not "just to read something". The only exception is explicit, written, per-task human authorization.
  3. Verify before you act, both layers. Session: is this MY port and MY profile? (lsof the port; know your own profile path.) Account: before EVERY write on any platform (post, reply, like, comment, repost, follow, DM), read the logged-in handle from the DOM in the same page context and assert it is the account the action is intended for. Mismatch = stop and report.

One session, one agent, always yours, always verified.
